# Контекст разработки TwitchTransparentChat

Документ фиксирует технические особенности, которые важно учитывать при изменении приложения. Архитектурное описание и диаграммы потоков находятся в [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Технологический стек

| Технология / пакет | Использование |
|---|---|
| Node.js | Главный процесс и сетевые операции |
| Electron 28 | Desktop-оболочка и renderer-процессы |
| HTML, CSS, JavaScript | Интерфейсы без отдельного frontend framework |
| `electron-store` | Постоянное хранение конфигурации |
| `electron-builder` | Сборка приложения |
| `electron-updater` | Обновления NSIS-сборки |
| `socks` | SOCKS5-прокси |
| Node.js `net`, `tls` | TCP/TLS подключение к Twitch IRC |
| Node.js `http`, `https` | Локальный HTTP-сервер и внешние API |
| Server-Sent Events | Доставка событий OBS Widget |

Production dependencies в `package.json`: `electron-store`, `electron-updater`, `socks`. Development dependencies: `electron`, `electron-builder`.

Команды package scripts включают запуск приложения и сборки: `npm start`, `npm run dist`, `npm run dist:portable`, `npm run dist:nsis`. Конфигурация сборки ориентирована на Windows (NSIS и portable).

## 2. Важные механизмы реализации

### 2.1. Twitch IRC

`twitch.js` реализует IRC-клиент на Node.js TLS без отдельной IRC-библиотеки. Подключение выполняется к `irc.chat.twitch.tv:6697`, используется анонимный ник вида `justinfan...`, отправляется `PASS SCHMOOPIIE` и запрашиваются capabilities для tags/commands. Это анонимное IRC-подключение, а не OAuth-авторизация Twitch.

Обрабатываются, среди прочего, `PRIVMSG`, `USERNOTICE`, `ROOMSTATE`, `CLEARMSG`, `CLEARCHAT`, `PING/PONG` и `RECONNECT`.

В реализации присутствуют watchdog, keep-alive и переподключение с ограниченной экспоненциальной задержкой. При изменениях этого модуля необходимо сохранять корректную обработку разрыва соединения, повторного подключения и порядка событий.

Анонимное подключение ограничивает доступность возможностей, требующих авторизации. Не следует предполагать, что IRC-события и права совпадают с авторизованным подключением.

### 2.2. Эмоции, бейджи и сетевые запросы

`emotes.js` содержит сетевой слой, SOCKS5-поддержку, кэширование и загрузку наборов эмоций Twitch, 7TV, BetterTTV и FrankerFaceZ. В обычном пути обработки сообщений `renderTwitchEmotes()` использует Twitch emote tags; сам факт загрузки сторонних наборов не означает, что 7TV/BTTV/FFZ автоматически участвуют в рендеринге каждого обычного сообщения. Не расширяйте это поведение в документации или коде без отдельной проверки соответствующего пути.

HTML бейджей формирует `twitch.js` (в том числе через `getBadgesHtml()`), а не `emotes.js`.

В реализации используются параллельная загрузка источников, кэш справочников, периодическое обновление и ограниченный кэш изображений. При включённом прокси для ресурсов используется протокол Electron `emote://`, обслуживаемый главным процессом. Также зарегистрирован протокол `card://` для изображений пользовательских плашек; OBS-сервер предоставляет для ресурсов маршруты `/img/*` и `/card/*`.

Изменения URL, источников CDN, кэширования или прокси нужно проверять вместе с отображением изображений в обоих renderer. Не следует обходить существующие механизмы `emote://` и `card://` без необходимости.

### 2.3. Конфигурация

`config.js` — обязательная точка нормализации настроек. Важные функции включают:

- `normalizeConfig()`;
- `sanitizeAppearance()`;
- `overlayView()`;
- `widgetView()`;
- `sanitizePreview()`;
- `normalizeChannel()`.

Конфигурация содержит общие параметры, отдельные настройки widget, пользовательские стили, назначения стилей и параметры ротации. При отсутствии отдельной конфигурации виджета начальное оформление может наследоваться от overlay.

Новые поля должны корректно обрабатываться при загрузке старой конфигурации, нормализации, сохранении, передаче в renderer и предпросмотре. Изменение только интерфейса настроек недостаточно.

### 2.4. IPC и preload

Renderer взаимодействует с главным процессом через API, предоставленный `preload.js`. При изменениях IPC необходимо сверять три стороны контракта:

1. обработчик/отправитель в `main.js`;
2. экспортируемый метод или подписку в `preload.js`;
3. место вызова в renderer (`index.html` или `settings.html`).

Не следует добавлять прямой доступ renderer к Node.js API вместо существующего моста.

### 2.5. Общий движок чата

`chat-view.js` используется и desktop overlay, и OBS Widget. Он управляет DOM сообщений, событиями, анимациями, ограничением количества элементов и визуальными настройками.

Любое изменение этого файла потенциально затрагивает оба renderer. Проверять нужно оба варианта, в том числе удаление сообщений, системные события, эмоции, бейджи, пользовательские стили и поведение при обновлении настроек.

### 2.6. OBS сервер

`widget-server.js` предоставляет локальные HTTP-маршруты и SSE. Сервер слушает `127.0.0.1`, ограничивает методы GET/HEAD и проверяет Host.

При изменении маршрутов, MIME types, раздачи статических ресурсов или SSE необходимо проверить подключение Browser Source, начальное получение состояния, повторное подключение и доставку обновлений. OBS Widget зависит от работающего desktop-приложения.

### 2.7. Обновления

`updater.js` проверяет GitHub Releases и использует `electron-updater` для NSIS-сборки. Для portable-сборки предусмотрен путь перехода к странице загрузки. Изменения обновления нужно проверять отдельно для обоих типов сборки.

## 3. Проверки при изменении компонентов

| Изменяемый компонент | Минимальные связанные проверки |
|---|---|
| `twitch.js` | Анонимное подключение к IRC, разбор команд/тегов, keep-alive, reconnect, формирование бейджей и события модерации |
| `emotes.js` | Twitch emote tags, загрузка наборов Twitch/7TV/BTTV/FFZ, CDN, кэш, прокси и загрузка изображений; отдельно проверить, какие источники реально участвуют в обычном рендеринге |
| `config.js` | Значения по умолчанию, старая конфигурация, нормализация, overlay/widget, пользовательские стили и rotation |
| `main.js` | Жизненный цикл окон, IPC, сохранение настроек, подключение Twitch, регистрация `emote://`/`card://`, tray и остановка сервера |
| `preload.js` | Совпадение API с IPC-обработчиками и всеми renderer-вызовами |
| `chat-view.js` | Desktop и OBS, обычные/системные сообщения, модерация, анимации и очистка DOM |
| `widget-server.js` | HTTP-маршруты, Host/method validation, `/img/*`, `/card/*`, SSE, heartbeat и переподключение OBS |
| `settings.html` | Загрузка/сохранение, валидация, предпросмотры overlay/widget, язык и статус сервера |
| `updater.js` | Проверка релиза, версии, Release Notes, NSIS и portable-сценарии |
| CSS/шрифты | Оба renderer, масштабирование, прозрачность и локальные ресурсы |

При изменении потока сообщений сохраняйте согласованность объекта сообщения между `twitch.js`, `main.js` и renderer, а также обе ветви доставки — IPC для desktop и SSE для OBS. Для настроек проверяйте путь `settings.html` → preload/IPC → `main.js` → `config.js`; для общих визуальных изменений — оба renderer.

Это рекомендации по областям регрессионной проверки, а не утверждение о наличии автоматизированных тестов.

## 4. Ограничения и технические особенности

- Twitch используется через анонимное IRC-подключение; функциональность, требующая авторизации, ограничена.
- OBS Widget обслуживается локальным процессом приложения и недоступен после его остановки.
- OBS-сервер привязан к loopback-интерфейсу `127.0.0.1`.
- Работа внешних эмоций зависит от сторонних API и CDN.
- Прокси влияет на сетевые запросы и доставку изображений.
- Overlay и Widget имеют отдельные настройки внешнего вида; их нельзя считать полностью одинаковыми конфигурациями.
- В `package.json` не обнаружены scripts для test/lint/check. В корневом дереве репозитория не обнаружена отдельная директория тестов.
- В корне не обнаружен `package-lock.json`.
- Конфигурация сборки содержит шаблон `assets/**`, но отдельная директория `assets` в проверенном дереве репозитория отсутствовала. Это наблюдение требует отдельной проверки только при работе со сборкой; само по себе оно не доказывает ошибку.

## 5. Практические правила разработки

1. Сначала определить затронутый контракт, а затем менять связанные модули минимальным набором.
2. Для изменений настроек проверять нормализацию и совместимость сохранённого `config.json`, а не только форму в `settings.html`.
3. Для сетевых изменений учитывать SOCKS5, Electron-протоколы `emote://` и `card://`, внешние CDN и обработку ошибок.
4. Не считать успешное чтение исходников подтверждением работоспособности runtime или сборки.
5. В репозитории нет обнаруженного стандартного набора test/lint scripts; явно указывать, какие проверки действительно запускались.

## 6. Границы достоверности

Документ основан на чтении исходников и конфигурации репозитория. Фактический запуск приложения, установка зависимостей, сборка Windows-пакетов, подключение к Twitch и тестирование OBS в рамках аудита не выполнялись.

При изменении реализации проверяйте актуальный код соответствующего модуля: документация описывает зафиксированное состояние и не заменяет исходный код.
